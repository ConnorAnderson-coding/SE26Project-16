# Apache JMeter 性能测试结果

测试日期：2026-07-28

## 验收结论

通过。

在 `activity` 核心表包含 10,000 条数据、100 个并发虚拟用户、
30 秒升压和 300 秒持续负载的条件下：

- 共完成 41,596 个请求；
- 错误数为 0，错误率为 0%；
- 总体平均响应时间为 34.90 ms；
- 总体 P95 响应时间为 67 ms；
- 总体 P99 响应时间为 86 ms；
- 最大响应时间为 434 ms；
- 吞吐量为 138.83 请求/秒。

平均、P95 和最大响应时间均小于 3,000 ms，错误率低于 1%，满足
“数据量不少于 10k、100 并发、响应时间小于 3 秒”的要求。

JMeter 下载包已经使用 Apache 官方 SHA-512 文件完成校验。

## 测试场景

1. 每个虚拟用户在启动后登录一次，提取 JWT。
2. 用户等待 300～1,000 ms，模拟正常思考时间。
3. 用户随机查询第 0～99 页活动列表，每页 20 条，按热度排序。
4. 用户随机查询 ID 为 1～10,000 的活动详情。
5. 步骤 2～4 循环执行至测试结束。

线程组配置：

| 配置项 | 数值 |
|---|---:|
| 并发虚拟用户 | 100 |
| 升压时间 | 30 秒 |
| 持续时间 | 300 秒 |
| 连接超时 | 3,000 ms |
| 响应读取超时 | 10,000 ms |
| 响应时间断言 | 3,000 ms |

本场景是读取为主的负载，因此 100 个线程共用只读测试账号。并发用户数由
JMeter 线程数表示，且每个线程分别完成登录并维护自己的 JWT 变量。

## 首轮失败与问题修复

首次 100 并发测试没有通过：

| 指标 | 修复前 |
|---|---:|
| 请求数 | 4,680 |
| 错误数 | 2,642 |
| 错误率 | 56.45% |
| 平均响应时间 | 5,583.66 ms |
| P95 | 10,013 ms |
| 最大响应时间 | 10,018 ms |
| 吞吐量 | 15.15 请求/秒 |

后端日志显示：

```text
HikariPool-1 - Connection is not available
total=10, active=10, idle=0, waiting≈190
```

根因是活动详情方法持有一个只读事务连接后，
`ActivityViewService.recordUniqueView()` 又通过 `REQUIRES_NEW`
申请第二个连接。当并发详情请求占满 10 个连接后，每个请求都持有第一个连接
并等待第二个连接，形成连接池饥饿。

最小修复：

1. 将 `ActivityService.getById()` 改为普通读写事务。
2. 删除 `ActivityViewService.recordUniqueView()` 的 `REQUIRES_NEW`，
   使详情读取和浏览记录写入共用同一个事务和数据库连接。

20 并发回归结果为 812 个请求、0 错误、平均 39 ms、最大 368 ms。
随后执行第二轮完整 100 并发测试，得到本报告的通过结果。

## 其他发现

这些问题不影响本次稳态响应时间验收，但建议后续处理：

1. 10,000 条活动下，`ActivityHotnessService` 启动时逐条更新 MySQL 和
   Redis，本机约需 78 秒，在此期间健康状态为 `OUT_OF_SERVICE`。建议改为批量
   更新或后台异步初始化。
2. Hibernate 启动时尝试修改 `favorite.user_id`，但该字段已被外键引用，
   因而产生非致命 DDL 警告。建议统一实体映射与 `schema.sql`，并在正式环境把
   `spring.jpa.hibernate.ddl-auto` 从 `update` 改为 `validate`，使用迁移脚本
   管理结构变化。
